Gateway Server Flow

Every request from the app enters through this one server. It does two jobs: it checks who is calling (using a Keycloak token), and it forwards the request to the right microservice (found through Eureka). It holds no business logic and no database.

The whole system on one page

The gateway is the blue box. Inside it a request passes two stages in a fixed order: security first, routing second. Keycloak and Eureka are helpers the gateway talks to; the client never talks to the eight services directly.

One request, step by step

This is what happens inside the gateway between arrow B and arrow E. Each step can end the request early; the status code tells you which step stopped it.

  1. Request arrives on port 5002

    Netty accepts it. The gateway is reactive (WebFlux), so no thread waits while the downstream service works.

  2. Token is checked, if one was sent

    If the request has Authorization: Bearer …, the signature is verified with Keycloak's public keys from /realms/master/protocol/openid-connect/certs. The keys are cached, so Keycloak is not called on every request. Expiry is checked too.

    bad or expired token → 401

  3. Roles are pulled out of the token

    KeyCloakRoleConverter reads realm_access.roles and every resource_access.*.roles, upper-cases each one and adds the ROLE_ prefix. This is how Keycloak's role names become something Spring Security understands.

  4. Path is matched against the access rules

    Rules in SecurityConfig are read top to bottom and the first one that matches decides. A path that matches no rule is denied.

    no token → 401 token, wrong role → 403

  5. Path is matched against the routes

    The eight routes in application.yml are tried in order. The first whose Path predicate matches gives the target, for example lb://booking-service.

    no route matches → 404

  6. Load balancer picks an instance

    lb:// means: ask the local copy of the Eureka registry for the instances of that service name and choose one (round-robin). The name becomes a real IP and port.

    service not registered → 503

  7. Request is forwarded unchanged

    Same path, same body, same headers. The Authorization header is passed along, so the service can read the same token to learn who the user is. The response streams back to the client.

    service's own response

How a Keycloak token becomes Spring roles

Keycloak stores roles in two places inside the token. The converter collects both, so it does not matter whether you created the role at realm level or on a client.

Inside the JWT

{
  "sub": "8f1c…",
  "realm_access": {
    "roles": ["customer"]
  },
  "resource_access": {
    "salon-app": {
      "roles": ["salon_owner"]
    }
  }
}

After KeyCloakRoleConverter

ROLE_CUSTOMER
ROLE_SALON_OWNER

"ROLE_" + role.toUpperCase()

hasAnyRole("CUSTOMER") looks for ROLE_CUSTOMER. Without the prefix and the upper-casing, every role check would fail with 403.

Starting it locally

The gateway depends on three things. Start them in this order so the first request works:

  1. Keycloak on :8080

    Realm master, with roles CUSTOMER, SALON_OWNER, ADMIN assigned to users.

  2. Eureka server on :8070

    The gateway registers itself here as gateway-server and downloads the list of services.

  3. The eight services

    Each must register under the exact name used after lb:// in the route table.

  4. The gateway on :5002

    ./mvnw spring-boot:run. Point the frontend at http://localhost:5002 and nowhere else. ./mvnw jib:build produces the Docker image.

What I would fix

Reading the code closely turned up five things. The first two change who can reach what, so they matter most.

  • security

    The SALON_OWNER-only rule never runs

    Rules are first-match-wins, and the broad rule 3 comes before the narrow rule 4. A CUSTOMER can call /api/category/salon-owner/** and the other owner-only paths; the gateway lets it through. Put the narrow rule above the broad one. Also remove /api/service-offering/** from the owner rule, or customers will lose access to listings once the order is fixed.

    SecurityConfig.java:28–40
  • broken

    Three routed path groups are blocked for everyone

    /salons/**, /api/admin/salons/** and /api/admin/users/** have routes but no access rule, so they always return 401 or 403, even for an ADMIN. Add rules for them (probably hasRole("ADMIN") for /api/admin/**) and end the list with an explicit anyExchange() line so the default is visible in the code.

    SecurityConfig.java:24–40 · application.yml:25,30
  • deploy

    Keycloak and Eureka addresses are fixed to localhost

    The JWKS URL is written twice: once in application.yml and again hard-coded in the reactiveJwtDecoder bean, which is the one actually used. Inside the Docker image localhost is the container itself, so token checks and Eureka registration will fail. Delete the bean (Spring Boot builds the same decoder from the yml property) and supply both URLs through environment variables.

    SecurityConfig.java:58–63 · application.yml:12,73
  • setup

    Users live in Keycloak's master realm

    master is Keycloak's own admin realm. App users and roles normally go in a separate realm, so an app account can never become a Keycloak administrator.

    application.yml:12
  • tidy

    Leftover config

    spring.jpa.show-sql does nothing here because the gateway has no database. The predicate /api/category/salon-owner** is already covered by /api/category/**. The discovery locator can be turned off since its routes are unreachable.

    application.yml:16–19,40,63–64

A rule order that does what the current one intends

exchanges
  .pathMatchers("/auth/**", "/api/notifications/ws/**").permitAll()
  .pathMatchers("/api/category/salon-owner/**",
                "/api/service-offering/salon-owner/**",
                "/api/notifications/salon-owner/**").hasRole("SALON_OWNER")
  .pathMatchers("/api/admin/**").hasRole("ADMIN")
  .pathMatchers("/salons/**", "/api/salons/**", "/api/category/**",
                "/api/notifications/**", "/api/bookings/**",
                "/api/payments/**", "/api/service-offering/**",
                "/api/users/**", "/users/**", "/api/reviews/**")
      .hasAnyRole("CUSTOMER", "SALON_OWNER", "ADMIN")
  .anyExchange().denyAll()

This assumes /salons/** needs a login and /api/admin/** is for admins. If salon browsing should be public, move /salons/** to the first line.
